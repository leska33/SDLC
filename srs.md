## 1. Введение {#1-introduction}
 
### 1.1 Назначение документа {#11-document-purpose}

Настоящий документ представляет собой Спецификацию требований к программному обеспечению (SRS) для веб-приложения «Wanderly». Его главная задача - четко определить границы проекта и зафиксировать **ЧТО** именно должна делать система, оставляя при этом пространство для инженерных решений относительно того, **КАК** это будет реализовано.

Документ выступает главным ориентиром для всех участников проекта, определяя зоны их ответственности:
* **Команда разработки** - использует спецификацию как основу для декомпозиции задач и реализации функциональности;
* **Инженеры по тестированию** - опираются на требования при составлении тест-планов и критериев приемки;
* **Заказчик** – сверяет по документу, насколько итоговый продукт закрывает его бизнес-потребности;
* **Преподаватель** - проводит оценку качества проектирования и проверку артефактов на протяжении жизненного цикла продукта.

Связанные документы: бизнес-требования от Заказчика, а также модель требований на языке SysMLv2 и структурные диаграммы пользовательских интерфейсов, созданные на этапе проектирования.

### 1.2 Область применения продукта {#12-product-scope}

**«Wanderly»** 0.1 - веб-приложение для поиска интересных мест, построения маршрутов экскурсий и навигации по интерактивной карте. Пользователь просматривает каталог достопримечательностей, фильтрует их, собирает маршрут и ориентируется по карте во время прогулки.

**Входит в область применения:**
* каталог достопримечательностей (описание, фото, категории, рейтинг, режим работы);
* поиск и фильтрация мест;
* построение и сохранение маршрутов экскурсии;
* интерактивная карта с маркерами мест и отображением маршрута;
* личный кабинет: избранные места и сохранённые маршруты;
* адаптивный веб-интерфейс для работы со смартфона и ПК.

**Не входит в область применения (в текущей версии):**
* аудиогиды и воспроизведение аудиорассказов;
* онлайн-оплата билетов и экскурсий;
* бронирование живых гидов в реальном времени;
* полноценное нативное мобильное приложение (iOS/Android);
* офлайн-режим с полной загрузкой данных города.

## 2. Обзор продукта {#2-product-overview}

### 2.1 Перспектива продукта {#21-product-perspective}

**«Wanderly»** - новый самостоятельный продукт. Ранее туристам и местным жителям приходилось пользоваться несколькими инструментами одновременно: сайтами-путеводителями для описания мест, картами для навигации и заметками/мессенджерами для сборки маршрута. Информация о достопримечательностях разрознена, а переход между сервисами во время прогулки неудобен. Приложение должно объединить каталог мест, построение маршрутов и интерактивную карту в одном веб-интерфейсе.

**Внешние системы и зависимости:**
* **Картографический сервис** (OpenStreetMap + Leaflet и/или Яндекс.Карты) - для отображения карты, маркеров мест и линии маршрута.
* **SMTP-сервер** (опционально на этапе MVP+) - для отправки уведомлений (например, подтверждение регистрации).

### 2.2 Функции продукта {#22-product-functions}

Основные функциональные возможности веб-приложения «Wanderly»:

* Просмотр каталога достопримечательностей.
* Поиск и фильтрация мест (категория, рейтинг, длительность посещения, район).
* Просмотр карточки места (описание, фото, режим работы, рейтинг).
* Построение и сохранение маршрутов из выбранных точек.
* Отображение мест и маршрутов на интерактивной карте.
* Добавление мест в избранное.
* Регистрация, авторизация и личный кабинет пользователя.
* Адаптивный интерфейс для смартфона и ПК.

### 2.3 Ограничения продукта {#23-product-constraints}

При разработке веб-приложения «Wanderly» должны соблюдаться следующие ограничения:

* **Только веб-версия:** Система реализуется исключительно как веб-приложение (без нативных приложений для iOS и Android).
* **Язык интерфейса:** Пользовательский интерфейс должен быть полностью на русском языке.
* **Без аудиогидов:** Воспроизведение аудиорассказов не входит в MVP.
* **Без онлайн-платежей:** Покупка билетов и бронирование экскурсий внутри приложения не предусмотрены.
* **Внешние интеграции:** Для отображения карты система должна использовать сторонний картографический API.
* **Законодательство:** Система должна соответствовать Закону РБ «О защите персональных данных».
* **Технологический стек:** Бэкенд-часть должна быть реализована на языке **Java** с использованием фреймворка **Spring Boot**. Фронтенд-часть должна быть реализована с использованием библиотеки **React**. База данных — **PostgreSQL**.

### 2.4 Характеристики пользователей {#24-user-characteristics}

Система «Wanderly» различает пользователей по их роли и правам доступа к функционалу. Основные классы пользователей представлены в таблице:

|          Роль              |            Описание            | Уровень подготовки|                            Права доступа                              |
| :------------------------- | :----------------------------- | :---------------- | :-------------------------------------------------------------------- |
| **Гость**                  | Неавторизованный посетитель    | Базовый           | Просмотр каталога, фильтров, карточек мест и карты                    |
| **Пользоват                | Зарегистрированный турист      | Базовый / средний | Всё доступное гостю + избранное, сохранение маршрутов, личный кабинет |
| **Администратор контента** | Сотрудник, наполняющий каталог | Средний           | Добавление и редактирование мест в каталоге                           |

**Особенности поведения и UX:**
* Пользователи часто используют приложение на смартфоне во время прогулки - требуется адаптивный дизайн (Mobile-First).
* Интерфейс должен быть интуитивно понятным: целевая аудитория включает туристов разного возраста.

### 2.5 Допущения и зависимости {#25-assumptions-and-dependencies}

**Допущения (предполагаемые условия):**
* **Браузеры:** Пользователи используют современные веб-браузеры с поддержкой HTML5, CSS3 и JavaScript (влияние при нарушении: некорректное отображение интерфейса).
* **Интернет:** Для загрузки карты и каталога требуется стабильное соединение (влияние при нарушении: карта и список мест могут не загрузиться).
* **Хостинг:** Серверная инфраструктура обеспечивает доступность системы на уровне не ниже 99% (влияние при нарушении: временная недоступность приложения).

**Зависимости (внешние системы и сервисы):**
* **Картографический API** (OpenStreetMap/Leaflet или Яндекс.Карты): отображение карты, маркеров и маршрута (влияние при нарушении: вместо карты показывается текстовый список координат/адресов).
* **SMTP-сервер** (при наличии email-уведомлений): доставка писем (влияние при нарушении: уведомления не отправляются, ошибка логируется).

## 3. Требования {#3-requirements}

### 3.1 Внешние интерфейсы {#31-external-interfaces}

#### 3.1.1 Пользовательские интерфейсы {#311-user-interfaces}

**REQ-INT-001: Главная страница (каталог и карта)**
* **Title:** Отображение каталога и карты.
* **Statement:** Система должна предоставлять главную страницу со списком мест, панелью фильтров и интерактивной картой с маркерами.
* **Rationale:** Это основной экран для поиска интересных мест.
* **Acceptance Criteria:** После открытия приложения пользователь видит список карточек мест и карту. При пустом результате поиска отображается сообщение «Ничего не найдено».
* **Verification Method:** Demonstration.

**REQ-INT-002: Интерфейс «Карточка места»**
* **Title:** Экран детальной информации о месте.
* **Statement:** Система должна предоставлять экран карточки места с описанием, рейтингом, фотогалереей, режимом работы, блоком построения маршрута, картой маршрута и действиями (избранное, поделиться, начать маршрут).
* **Rationale:** Пользователь должен получить достаточно информации о месте и быстро добавить его в маршрут.
* **Acceptance Criteria:** Все перечисленные блоки отображаются на странице и корректно адаптируются под экран.
* **Verification Method:** Demonstration.

**REQ-INT-003: Панель поиска и фильтров**
* **Title:** Фильтрация каталога.
* **Statement:** Система должна предоставлять интерфейс фильтрации по категориям, рейтингу и длительности посещения, а также строку поиска по названию.
* **Rationale:** Ускоряет поиск подходящих мест.
* **Acceptance Criteria:** Применение фильтра обновляет список мест и маркеры на карте.
* **Verification Method:** Test.

**REQ-INT-004: Интерактивная карта**
* **Title:** Виджет карты.
* **Statement:** Система должна предоставлять интерактивную карту с маркерами мест и отображением выбранного маршрута.
* **Rationale:** Помогает ориентироваться в пространстве города.
* **Acceptance Criteria:** Клик по маркеру открывает краткую информацию о месте / переход к карточке. Маршрут отображается линией на карте.
* **Verification Method:** Demonstration.

**REQ-INT-005: Страница авторизации и регистрации**
* **Title:** Вход и регистрация пользователей.
* **Statement:** Система должна предоставлять страницу для регистрации и ввода email/пароля.
* **Rationale:** Необходимо для сохранения избранного и маршрутов.
* **Acceptance Criteria:** При неверном пароле выводится сообщение «Неверный пароль».
* **Verification Method:** Test.

**REQ-INT-006: Личный кабинет**
* **Title:** Избранное и сохранённые маршруты.
* **Statement:** Система должна предоставлять страницу личного кабинета со списками избранных мест и сохранённых маршрутов.
* **Rationale:** Пользователь должен быстро возвращаться к ранее выбранным местам и маршрутам.
* **Acceptance Criteria:** После авторизации в кабинете отображаются сохранённые сущности пользователя.
* **Verification Method:** Demonstration.

**Юзабилити и доступность:** Интерфейс должен соответствовать принципам адаптивного дизайна (Mobile-First) и обеспечивать понятные состояния ошибок. Структурные диаграммы экранов приведены в разделе 5.

#### 3.1.2 Аппаратные интерфейсы {#312-hardware-interfaces}

**REQ-INT-007: Адаптивность под экраны**
* **Title:** Поддержка мобильных устройств и ПК.
* **Statement:** Система должна корректно отображаться на устройствах с разрешением экрана от 320px до 2560px.
* **Rationale:** Пользователи будут заходить как с телефонов во время прогулки, так и с компьютеров при планировании.
* **Acceptance Criteria:** Верстка не ломается на экранах шириной 375px (смартфон) и 1920px (ПК).
* **Verification Method:** Test.

**REQ-INT-008: Поддержка устройств ввода**
* **Title:** Ввод данных.
* **Statement:** Система должна поддерживать управление с помощью клавиатуры, мыши, а также touch-ввода на сенсорных экранах.
* **Rationale:** Обеспечение базовой доступности.
* **Acceptance Criteria:** Все интерактивные элементы кликабельны и доступны для нажатия пальцем.
* **Verification Method:** Demonstration.

#### 3.1.3 Программные интерфейсы {#313-software-interfaces}

**REQ-INT-009: Интеграция с картографическим API**
* **Title:** Отображение карты.
* **Statement:** Система должна интегрироваться с внешним картографическим API (OpenStreetMap/Leaflet или Яндекс.Карты) для отображения мест и маршрутов.
* **Rationale:** Визуализация геопозиции — ключевая ценность продукта.
* **Acceptance Criteria:** Маркеры отображаются по координатам. При таймауте API (более 5 секунд) выводится текстовая заглушка.
* **Verification Method:** Demonstration.

**REQ-INT-010: REST API для связи Frontend и Backend**
* **Title:** Взаимодействие клиента и сервера.
* **Statement:** Бэкенд-часть должна предоставлять REST API (в формате JSON) для взаимодействия с React-фронтендом.
* **Rationale:** Обеспечивает разделение клиентской и серверной логики.
* **Acceptance Criteria:** Все запросы возвращают корректные HTTP-статусы и JSON.
* **Verification Method:** Test (Postman).

**REQ-INT-011: Отправка email через SMTP (опционально для MVP+)**
* **Title:** Email-уведомления.
* **Statement:** Система должна иметь возможность отправлять email-уведомления (например, подтверждение регистрации) через SMTP-сервер.
* **Rationale:** Информирование пользователя.
* **Acceptance Criteria:** Письмо приходит на указанный адрес. При недоступности SMTP ошибка логируется.
* **Verification Method:** Test.

### 3.2 Функциональные требования {#32-functional}

#### Каталог и карточка места

**REQ-FUNC-001: Просмотр и фильтрация каталога**
* **Statement:** Система должна предоставлять каталог достопримечательностей с возможностью поиска и фильтрации.
* **Rationale:** Базовая функция продукта — быстрый поиск интересных мест.
* **Acceptance Criteria:** Пользователь видит список мест; фильтры и поиск изменяют выдачу.
* **Verification Method:** Test
* **More Information:** Негативный сценарий: при отсутствии результатов показывается понятное сообщение.

**REQ-FUNC-002: Просмотр карточки места**
* **Statement:** Система должна отображать детальную информацию о месте: название, описание, рейтинг, фото, режим работы, координаты.
* **Rationale:** Пользователь принимает решение о посещении на основе полной карточки.
* **Acceptance Criteria:** При открытии существующего места все доступные поля отображаются корректно.
* **Verification Method:** Demonstration
* **More Information:** Если место удалено/не найдено — сообщение «Место не найдено» и HTTP 404 на API.

#### Маршруты и карта

**REQ-FUNC-003: Построение и сохранение маршрута**
* **Statement:** Система должна позволять авторизованному пользователю добавлять места в маршрут, менять порядок точек, сохранять и открывать сохранённые маршруты.
* **Rationale:** Ключевая бизнес-ценность — собрать экскурсию из интересных точек.
* **Acceptance Criteria:** Добавленное место появляется в списке точек маршрута; после сохранения маршрут доступен в личном кабинете.
* **Verification Method:** Test
* **More Information:** Гость может собирать черновик маршрута в рамках сессии, но для сохранения требуется авторизация.

**REQ-FUNC-004: Отображение мест и маршрута на карте**
* **Statement:** Система должна отображать маркеры мест и линию выбранного маршрута на интерактивной карте.
* **Rationale:** Навигация и планирование пути.
* **Acceptance Criteria:** Маркеры соответствуют координатам мест; маршрут рисуется между точками в заданном порядке.
* **Verification Method:** Demonstration
* **More Information:** При недоступности картографического API показывается текстовый список точек маршрута.

#### Избранное и аккаунт

**REQ-FUNC-005: Избранные места**
* **Statement:** Система должна позволять авторизованному пользователю добавлять и удалять места из избранного.
* **Rationale:** Быстрый доступ к понравившимся объектам.
* **Acceptance Criteria:** Место появляется в списке избранного и удаляется по повторному действию.
* **Verification Method:** Test

**REQ-FUNC-006: Регистрация, авторизация и выход**
* **Statement:** Система должна обеспечивать регистрацию и вход пользователей по email и паролю, а также выход из аккаунта.
* **Rationale:** Необходимо для сохранения избранного и маршрутов.
* **Acceptance Criteria:** Успешный вход открывает личный кабинет; при неверном пароле — ошибка; после выхода сессия уничтожается.
* **Verification Method:** Test
* **More Information:** Пароли хранятся в хешированном виде (BCrypt).

**REQ-FUNC-007: Управление контентом каталога (после MVP)**
* **Statement:** Система должна позволять администратору контента добавлять и редактировать места в каталоге.
* **Rationale:** Актуальность данных о достопримечательностях.
* **Acceptance Criteria:** Новое место появляется в каталоге и на карте после сохранения.
* **Verification Method:** Test
* **More Information:** В MVP наполнение может выполняться через скрипты/миграции без UI-админки.

### 3.3 Качество обслуживания {#33-quality-of-service}

#### 3.3.1 Производительность {#331-performance}

Все целевые показатели измеряются при стационарной нагрузке (до 100 одновременно активных пользователей) в условиях стандартного широкополосного интернет-соединения.

**REQ-PERF-001: Время загрузки страниц**
* **Statement:** Время полной загрузки (First Contentful Paint) главной страницы и карточки места не должно превышать **3 секунд**.
* **Rationale:** Длительная загрузка снижает удобство использования во время прогулки.
* **Acceptance Criteria:** 95% запросов к страницам выполняются быстрее 3000 мс.
* **Verification Method:** Test
* **More Information:** Относится к REQ-INT-001 и REQ-INT-002.

**REQ-PERF-002: Время отклика API**
* **Statement:** Среднее время обработки запроса к REST API (бэкенд Spring Boot) не должно превышать **300 мс** для 90% запросов (без учёта внешних картографических тайлов).
* **Rationale:** Быстрый отклик сервера обеспечивает плавную работу интерфейса.
* **Acceptance Criteria:** p90 времени ответа API < 300 мс.
* **Verification Method:** Analysis
* **More Information:** Касается REQ-INT-010.

**REQ-PERF-003: Объём каталога**
* **Statement:** Система должна выдерживать хранение не менее **5 000** мест в каталоге без существенной деградации поиска и фильтрации.
* **Rationale:** Масштабируемость на этапе роста контента.
* **Acceptance Criteria:** При 5 000 записей время выборки с фильтрами не увеличивается более чем на 20% относительно базового теста.
* **Verification Method:** Analysis

#### 3.3.2 Безопасность {#332-security}

**REQ-SEC-001: Хеширование паролей**
* **Statement:** Система не должна хранить пароли в открытом виде; пароли должны храниться как хеши BCrypt.
* **Rationale:** Защита аккаунтов при утечке БД.
* **Acceptance Criteria:** В таблице пользователей поле пароля содержит хеш.
* **Verification Method:** Inspection

**REQ-SEC-002: Защита API (Авторизация)**
* **Statement:** Доступ к защищённым эндпоинтам (избранное, сохранение маршрутов) должен требовать валидный токен авторизации.
* **Rationale:** Запрет неавторизованных действий.
* **Acceptance Criteria:** Запрос без токена возвращает `401 Unauthorized`.
* **Verification Method:** Test (Postman)

**REQ-SEC-003: Защита от SQL-инъекций**
* **Statement:** Взаимодействие с БД должно выполняться через параметризованные запросы / ORM (JPA/Hibernate).
* **Rationale:** Предотвращение SQL Injection.
* **Acceptance Criteria:** Вредоносный ввод в формы не приводит к выполнению произвольного SQL.
* **Verification Method:** Test

**REQ-SEC-004: Валидация входящих данных**
* **Statement:** Все пользовательские данные должны проходить серверную валидацию.
* **Rationale:** Защита от XSS и нарушения целостности данных.
* **Acceptance Criteria:** Некорректные данные возвращают `400 Bad Request`.
* **Verification Method:** Test

**REQ-SEC-005: Разграничение прав**
* **Statement:** Пользователь может изменять только свои избранные места и маршруты.
* **Rationale:** Целостность данных пользователей.
* **Acceptance Criteria:** Попытка изменить чужой маршрут возвращает `403 Forbidden`.
* **Verification Method:** Test

**REQ-SEC-006: HTTPS**
* **Statement:** Данные между клиентом и сервером должны передаваться по HTTPS.
* **Rationale:** Защита от перехвата.
* **Acceptance Criteria:** HTTP перенаправляется на HTTPS (в продакшен-окружении).
* **Verification Method:** Demonstration

**REQ-SEC-007: Согласие на обработку ПДн**
* **Statement:** При регистрации пользователь должен явно дать согласие на обработку персональных данных.
* **Rationale:** Закон РБ «О защите персональных данных».
* **Acceptance Criteria:** Без согласия кнопка регистрации неактивна.
* **Verification Method:** Test

#### 3.3.3 Надёжность {#333-reliability}

**REQ-REL-001: Обработка ошибок картографического API**
* **Statement:** При недоступности карт система не должна падать; должна отображаться понятная заглушка.
* **Rationale:** Пользователь продолжает работу с каталогом и маршрутом.
* **Acceptance Criteria:** При таймауте карты > 5 с показывается сообщение «Карта временно недоступна».
* **Verification Method:** Test

**REQ-REL-002: Таймауты запросов**
* **Statement:** Запросы к БД и внешним API должны иметь timeout.
* **Rationale:** Предотвращение зависания потоков сервера.
* **Acceptance Criteria:** При отсутствии ответа БД > 10 с пользователь получает ошибку 503.
* **Verification Method:** Test

**REQ-REL-003: Защита от двойного клика**
* **Statement:** При сохранении маршрута кнопка должна блокироваться до ответа сервера.
* **Rationale:** Предотвращение дублей.
* **Acceptance Criteria:** Повторный клик в течение ожидания ответа игнорируется.
* **Verification Method:** Demonstration

#### 3.3.4 Доступность {#334-availability}

**REQ-AVAIL-001: Целевой уровень доступности (SLO)**
* **Statement:** Доступность системы должна составлять не менее **99%** в месяц (для учебного MVP допустимо 95%).
* **Rationale:** Пользователи планируют маршруты заранее.
* **Acceptance Criteria:** Суммарный простой не превышает установленный порог.
* **Verification Method:** Analysis

**REQ-AVAIL-002: Окна обслуживания**
* **Statement:** Плановые работы следует проводить в ночное время (03:00–05:00 по минскому времени).
* **Rationale:** Минимизация влияния на пользователей.
* **Acceptance Criteria:** Во время работ отображается заглушка об обновлении.
* **Verification Method:** Demonstration

**REQ-AVAIL-003: Восстановление после сбоя**
* **Statement:** При аварийном завершении сервера система должна автоматически перезапуститься; RTO ≤ **15 минут**.
* **Rationale:** Снижение простоя.
* **Acceptance Criteria:** После имитации падения процесса сервис поднимается автоматически (Docker `restart: always` / аналог).
* **Verification Method:** Test

#### 3.3.5 Наблюдаемость {#335-observability}

**REQ-OBS-001: Формат логов**
* **Statement:** События бэкенда должны логироваться с датой/временем, уровнем (INFO/WARN/ERROR) и именем модуля.
* **Rationale:** Диагностика инцидентов.
* **Acceptance Criteria:** Успешное сохранение маршрута даёт INFO; ошибка валидации — WARN.
* **Verification Method:** Inspection

**REQ-OBS-002: Защита секретов в логах**
* **Statement:** Пароли и токены не должны попадать в логи.
* **Rationale:** Защита персональных данных.
* **Acceptance Criteria:** В логе входа фиксируются email и статус, но не пароль.
* **Verification Method:** Inspection

**REQ-OBS-003: Health Check**
* **Statement:** Система должна предоставлять эндпоинт `/api/health`.
* **Rationale:** Мониторинг работоспособности.
* **Acceptance Criteria:** GET `/api/health` возвращает `{"status":"UP"}` и код 200.
* **Verification Method:** Demonstration

### 3.4 Соответствие стандартам {#34-compliance}

**REQ-COMP-001: Защита персональных данных**
* **Statement:** Обработка ПДн должна соответствовать Закону РБ № 99-З.
* **Rationale:** Юридические требования и доверие пользователей.
* **Acceptance Criteria:** Есть согласие при регистрации и политика конфиденциальности.
* **Verification Method:** Inspection

**REQ-COMP-002: Лицензии внешних API**
* **Statement:** Использование картографических сервисов должно соответствовать их Terms of Service / требованиям атрибуции.
* **Rationale:** Избежать блокировки ключей API.
* **Acceptance Criteria:** В интерфейсе размещена необходимая атрибуция картографического провайдера.
* **Verification Method:** Inspection

**REQ-COMP-003: Пользовательское соглашение**
* **Statement:** Доступ к EULA и Политике конфиденциальности должен быть до завершения регистрации.
* **Rationale:** Юридическое оформление отношений.
* **Acceptance Criteria:** Ссылки открывают документы в новой вкладке.
* **Verification Method:** Demonstration

### 3.5 Проектирование и реализация {#35-design-and-implementation}

#### 3.5.1 Установка {#351-installation}

**REQ-INST-001: Контейнеризация**
* **Statement:** Бэкенд (Spring Boot) и PostgreSQL должны поставляться в Docker; запуск описывается в `docker-compose.yml`.
* **Rationale:** Воспроизводимость окружения.
* **Acceptance Criteria:** `docker-compose up -d` поднимает сервисы без ошибок.
* **Verification Method:** Demonstration

**REQ-INST-002: Переменные окружения**
* **Statement:** Секреты (пароль БД, JWT, ключи API) передаются через `.env`, а не хранятся в коде.
* **Rationale:** Безопасность репозитория.
* **Acceptance Criteria:** В репозитории есть `.env.example` без реальных секретов.
* **Verification Method:** Inspection

#### 3.5.2 Сборка и поставка {#352-build-and-delivery}

**REQ-BUILD-001: Сборка бэкенда**
* **Statement:** Сборка Java-части через Maven, результат — исполняемый `.jar`.
* **Acceptance Criteria:** `mvn clean package` завершается BUILD SUCCESS.
* **Verification Method:** Test

**REQ-BUILD-002: Сборка фронтенда**
* **Statement:** Сборка React через `npm run build`, результат — статика в `dist`.
* **Acceptance Criteria:** Команда завершается успешно, папка `dist` создана.
* **Verification Method:** Test

**REQ-BUILD-003: Фиксация зависимостей**
* **Statement:** Версии зависимостей фиксируются в `pom.xml` и `package-lock.json`.
* **Acceptance Criteria:** `package-lock.json` не игнорируется `.gitignore`.
* **Verification Method:** Inspection

#### 3.5.3 Распределение {#353-distribution}

**REQ-DIST-001: Централизованное развертывание**
* **Statement:** На этапе MVP компоненты размещаются на одном сервере/хосте.
* **Acceptance Criteria:** Сервисы доступны по одному доменному имени/адресу.
* **Verification Method:** Inspection

#### 3.5.4 Сопровождаемость {#354-maintainability}

**REQ-MAINT-001: Стандарты кодирования**
* **Statement:** Код Java/JS должен иметь осмысленные имена и соответствовать общепринятым стандартам.
* **Verification Method:** Inspection

**REQ-MAINT-002: Модульная архитектура**

**REQ-MAINT-003: README**

**REQ-MAINT-004: Git и Pull Request**
* **Statement:** Разработка ведётся в отдельных ветках с осмысленными коммитами и слиянием через PR.
* **Verification Method:** Inspection

#### 3.5.5 Повторное использование {#355-reusability}

**REQ-REUSE-001: UI-компоненты React**
* **Statement:** Кнопки, карточки мест, фильтры реализуются как переиспользуемые компоненты.

**REQ-REUSE-002: Бизнес-логика Spring Boot**

**REQ-REUSE-003: Стабильное REST API**
